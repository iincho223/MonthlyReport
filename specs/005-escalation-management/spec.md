# Feature Specification: エスカレーション管理

**Feature Branch**: `005-escalation-management`

**Created**: 2026-08-22

**Status**: Draft

**Input**: User description: "月報とは別に、対象メンバーの問題事案（長期欠勤など）を管理するエスカレーション機能。TL以上（TL/GL/OM）のみ起票（新規作成）でき、NG/TMはエスカレーション機能自体にアクセスできない。起票時は対象メンバー氏名・所属チーム・タイトル・重要度（LOW/MEDIUM/HIGH）・ステータス（PENDING/ONGOING/RESOLVED）・対応期日（必須）を入力する。対応担当者は任意で設定できる。一覧・詳細の可視範囲はロールにより異なる：TLは自チーム＋自分が起票したもの、GL・SMは自営業所全件、SPは自分が担当のもの、OM・SAは全件（SAはマスク表示）。詳細画面ではステータス更新ボタン・対応ログのタイムライン表示・ログ追記欄がある。対応ログは追記のみで削除不可。ステータスはPENDING/ONGOING/RESOLVED間を双方向に遷移でき、RESOLVEDにする場合は完了期日を必ず設定する。対応担当者はTL以上であればいつでも変更できるが、一度設定すると未設定には戻せない。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 問題事案をエスカレーションとして起票する (Priority: P1)

TL以上のロールを持つユーザーが、対象メンバーに関する問題事案を新規に起票する。

**Why this priority**: エスカレーション機能全体の起点であり、これがなければ一覧・詳細・対応管理のいずれも成立しない。

**Independent Test**: TL以上のロールのユーザーが必須項目（対象メンバー氏名・所属チーム・タイトル・重要度・ステータス・対応期日）を入力して起票し、エスカレーションが1件作成されることを確認するだけで完結してテストできる。

**Acceptance Scenarios**:

1. **Given** TL以上のロールのユーザーが起票画面を開いている、**When** 対象メンバー氏名・所属チーム・タイトル・重要度・ステータス・対応期日を入力して起票する、**Then** 新しいエスカレーションが作成される。
2. **Given** TL以上のロールのユーザーが起票画面を開いている、**When** 対応期日を入力せずに起票しようとする、**Then** システムは起票を許可しない。
3. **Given** NGまたはTMロールのユーザーが、**When** エスカレーション機能へのアクセスまたは起票を試みる、**Then** システムはアクセス・起票を許可しない。
4. **Given** TL以上のロールのユーザーが起票画面を開いている、**When** 対応担当者を指定せずに起票する、**Then** 対応担当者未設定のままエスカレーションが作成される。

---

### User Story 2 - 自分の可視範囲内のエスカレーション一覧を確認する (Priority: P1)

TL以上のロールを持つユーザーが、自分のロールに応じた可視範囲のエスカレーション一覧を確認できる。

**Why this priority**: 起票（P1）と並ぶ本機能の中核目的であり、一覧なしでは個々の事案を発見・管理できない。

**Independent Test**: 各ロールでログインし、エスカレーション一覧に表示される件数・対象が業務仕様のロール別可視範囲と一致することを確認するだけで完結してテストできる。

**Acceptance Scenarios**:

1. **Given** TLロールでログインしている、**When** エスカレーション一覧を開く、**Then** 自チームに関するもの、および自分が起票したものが表示される。
2. **Given** GLまたはSMロールでログインしている、**When** エスカレーション一覧を開く、**Then** 自営業所のエスカレーションが全件表示される。
3. **Given** SPロールでログインしている、**When** エスカレーション一覧を開く、**Then** 自分が対応担当者となっているエスカレーションが表示される。
4. **Given** OMロールでログインしている、**When** エスカレーション一覧を開く、**Then** エスカレーションが全件表示される。
5. **Given** SAロールでログインしている、**When** エスカレーション一覧を開く、**Then** エスカレーションは全件表示されるが内容はマスクされた状態で表示される。
6. **Given** 一覧が表示されている、**When** 各項目を確認する、**Then** ステータスバッジ・重要度・タイトル・対象メンバー氏名・起票者名が表示されている。

---

### User Story 3 - エスカレーションの対応状況を更新する (Priority: P1)

可視範囲内のエスカレーションに対し、権限を持つユーザーがステータス・重要度・対応担当者を更新する。

**Why this priority**: エスカレーションは事案が解決するまで継続的に更新される前提のため、起票・一覧確認と並ぶ中核機能とする。

**Independent Test**: 更新権限を持つユーザーがステータスをPENDINGからONGOINGへ変更し、変更が反映されることを確認するだけで完結してテストできる。

**Acceptance Scenarios**:

1. **Given** 更新権限を持つユーザーがエスカレーション詳細を開いている、**When** ステータスをPENDING→ONGOING→RESOLVEDの順、または逆順に変更する、**Then** ステータスが変更後の値に更新される。
2. **Given** ステータスをRESOLVEDに変更しようとしている、**When** 完了期日を設定せずに変更を試みる、**Then** システムは変更を許可しない。
3. **Given** 更新権限を持つユーザーが、**When** 重要度をLOW/MEDIUM/HIGHの間で変更する、**Then** いつでも変更が反映される。
4. **Given** TL以上のロールのユーザーが、**When** 対応担当者を別のユーザーに変更する、**Then** 対応担当者が変更後のユーザーに更新される。
5. **Given** 対応担当者が設定済みのエスカレーションに対し、**When** 対応担当者を未設定に戻そうとする、**Then** システムは変更を許可しない。
6. **Given** 自分の可視範囲外のエスカレーションに対し、**When** 更新を試みる、**Then** システムは更新を許可しない。

---

### User Story 4 - 対応履歴をログとして記録する (Priority: P2)

エスカレーションの詳細画面から、対応内容を対応ログとして随時追記し、時系列で確認できる。

**Why this priority**: 対応状況の更新（P1）に付随する記録機能であり、事案対応の経過を残す価値はあるが、ステータス管理そのものより優先度は一段低いとする。

**Independent Test**: 詳細画面でログを1件追記し、対応履歴タイムラインに追加されることを確認するだけで完結してテストできる。

**Acceptance Scenarios**:

1. **Given** エスカレーション詳細画面を開いている、**When** 対応ログ入力欄に内容を入力して保存する、**Then** 対応履歴タイムラインに日時・記録者・内容とともに新しいログが追加される。
2. **Given** 対応履歴が複数件存在する、**When** タイムラインを確認する、**Then** 過去に記録したログは削除・変更されず、追記のみが反映される。

### Edge Cases

- 対応期日が過去日に設定された状態でステータスがPENDINGのまま放置された場合の扱い（本仕様では期日超過時の自動処理は定義しない）。
- 対象メンバー・所属チームが自由入力/選択のため、既存の組織情報と一致しない値が入力された場合の扱い。
- 起票直後に対応担当者が未設定のまま一覧・詳細に表示される場合、担当者欄は「未設定」と表示される。
- 可視範囲外のユーザーがURL等で直接エスカレーション詳細へアクセスしようとした場合、システムはアクセスを拒否する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはNG・TMロールに対し、エスカレーション機能（一覧・詳細・起票のいずれも）へのアクセスを許可してはならない。
- **FR-002**: システムはTL・GL・OMロールのユーザーにのみエスカレーションの起票を許可しなければならない。
- **FR-003**: システムは起票時に対象メンバー氏名・所属チーム・タイトル・重要度・ステータス・対応期日を必須項目として要求しなければならない。
- **FR-004**: システムは起票時に対応担当者を任意項目として扱い、未指定でも起票を許可しなければならない。
- **FR-005**: システムはユーザーのロールに応じてエスカレーション一覧・詳細の可視範囲を制御しなければならない（TL: 自チーム+自分が起票したもの／GL・SM: 自営業所全件／SP: 自分が担当のもの／OM: 全件／SA: 全件をマスク表示）。
- **FR-006**: システムはエスカレーション一覧に、ステータスバッジ・重要度・タイトル・対象メンバー氏名・起票者名を表示しなければならない。
- **FR-007**: システムはステータスをPENDING・ONGOING・RESOLVEDの間で双方向に変更できなければならない。
- **FR-008**: システムはステータスをRESOLVEDに変更する際、完了期日の設定を必須としなければならない。
- **FR-009**: システムは重要度をLOW・MEDIUM・HIGHの間でいつでも変更できるようにしなければならない。
- **FR-010**: システムはTL以上のロールのユーザーに対し、対応担当者をいつでも変更できるようにしなければならない。
- **FR-011**: システムは一度設定された対応担当者を未設定（null）に戻す変更を拒否しなければならない。
- **FR-012**: システムは自分の可視範囲外のエスカレーションに対する更新操作を拒否しなければならない。
- **FR-013**: システムは対応ログの追記を随時可能にし、既存のログの削除・変更を許可してはならない。
- **FR-014**: システムは対応履歴を日時・記録者・内容とともに時系列（タイムライン）で表示しなければならない。

### Key Entities

- **エスカレーション**: タイトル、対象メンバー氏名、対象チーム、詳細内容、重要度（LOW/MEDIUM/HIGH）、ステータス（PENDING/ONGOING/RESOLVED）、対応期日、完了期日（RESOLVED時のみ必須）、対応担当者、起票者（氏名・ロール）、更新日時を持つ。
- **対応ログ**: エスカレーションに紐づき、記録日時・記録者・内容を持つ。追記のみ可能で、既存ログの削除・変更はできない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: TL以上のロールのユーザーの100%が、必須項目を満たした起票を完了できる。
- **SC-002**: 各ロールで表示されるエスカレーション件数が、業務仕様上の可視範囲定義と100%一致する。
- **SC-003**: RESOLVEDへのステータス変更試行のうち、完了期日未設定のものの100%が拒否される。
- **SC-004**: 対応担当者を未設定に戻そうとする変更試行の100%が拒否される。
- **SC-005**: 追記された対応ログの100%が、削除・変更されることなくタイムラインに保持される。

## Assumptions

- 対象メンバー氏名・所属チームは自由入力/選択項目とし、既存のユーザー・組織マスタとの厳密な整合チェックは本仕様の対象外とする。
- エスカレーションの削除機能は本仕様には含めない（既存業務仕様に削除操作の記載がないため、対象外とする）。
- 通知（起票時・ステータス変更時の関係者への通知）は本仕様の対象外とし、画面・データの状態管理のみを対象とする。
