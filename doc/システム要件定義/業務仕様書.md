# 月報管理システム 業務仕様書

## 1. 目的

本書は、ロール定義・可視範囲・業務制約・UI/データ仕様など、実装・設計判断の拠り所となる業務ルールを定義する。
仕様変更を伴う実装・設計を行う場合は、必ず本書との整合を確認する。

## 2. ロールと可視範囲

### 2.1 グループ定義

- チーム: エンジニアのメンバーの集合。
- グループ: エンジニアのチームの集合。グループは営業所に対応する。
- 営業所: グループの集合。
- 営業: 営業所に所属する営業担当の集合。
- システム管理者: 全ての営業所・グループ・チームを横断的に管理する。

### 2.2 ロール定義

- NG: 月報の提出や閲覧は不可。エスカレーション機能へのアクセス不可。
- TM: 月報提出と自分の月報のみ。エスカレーション機能へのアクセス不可。
- TL: 自分の月報の提出、自チームの月報とエスカレーションを管理。
- GL: 自分の月報の提出、自グループの月報とエスカレーションを管理。自グループのユーザーおよびチームの登録・削除が可能。
- OM: 営業所に所属する全件の月報とエスカレーションを管理。自営業所のユーザーおよびグループ・チームの登録・削除が可能。
- SP: 自身が担当となっているエスカレーションを管理。所属営業所のエンジニア・SP・SMのユーザーを登録・削除可能。
- SM: 営業所に所属する全てのエスカレーションを管理。所属営業所のエンジニア・SP・SMのユーザーを登録・削除可能。
- SA: 月報とエスカレーションの内容はマスクして表示。営業所の追加やユーザー管理など全てのロールを横断的に管理。
- ロールの上下関係: `NG < TM < TL < GL < OM`、`SP` と `SM` は営業担当者・支店長としてエスカレーション管理の特例ロール、`SA` は全てのロールを横断的に管理する特例ロール。

### 2.3 月報

- NG: 月報の提出不可。月報の閲覧不可。
- TM: 自分の月報のみ。
- TL: 自分の月報 + 同一チームの月報。
- GL: 自分の月報 + 同一グループの月報。
- OM: 自分の月報 + 営業所に所属する全件の月報。
- SP: 自分が担当となっている月報。
- SM: 営業所に所属する全件の月報。
- SA: 月報自体へは画面からアクセス可能。月報の内容はマスクしたものを表示。

### 2.4 エスカレーション

- NG: エスカレーション機能へのアクセス不可。
- TM: エスカレーション機能へのアクセス不可。
- TL: 自チームに関するエスカレーション + 自分が起票したエスカレーション。
- GL: 自グループのエスカレーション全件。
- OM: 営業所に所属する全件のエスカレーション。
- SP: 自分が担当となっているエスカレーション全件。
- SM: 営業所に所属する全件のエスカレーション。
- SA: エスカレーション自体へは画面からアクセス可能。エスカレーションの内容はマスクしたものを表示。

### 2.5 ユーザー管理

- NG: 不可。
- TM（メンバー／エンジニア）: 不可。
- TL: 不可。
- GL: 自グループおよび自グループ配下チームへエンジニアを登録・削除可。
- OM: 自営業所の全グループ・チームへエンジニアを登録・削除可。
- SP: 所属営業所にエンジニア・SP・SMのユーザーを登録・削除可。
- SM: 所属営業所にエンジニア・SP・SMのユーザーを登録・削除可。
- SA: 全ユーザーを登録・削除可（全権限）。

### 2.6 組織管理（グループ・チーム）

- NG: 不可。
- TM: 不可。
- TL: 不可。
- GL: 自グループへのチーム登録・削除可。グループ自体の登録・削除は不可。
- OM: グループおよびチームの登録・削除可（全グループ・チーム対象）。
- SP: 不可。
- SM: 不可。
- SA: 全グループ・チームを登録・削除可（全権限）。

## 3. 業務制約

### 3.1 月報

- 月報の重複禁止: 同一ユーザーによる同一月（YYYY-MM）の月報作成は 1 件。
- 編集権限: 月報は作成者本人のみ。
- 削除権限: 月報は作成者本人、または OM のみ。
- 回答（フィードバック）: TL 以上かつ他者の月報に対してのみ可能。

### 3.2 エスカレーション

- 起票権限: TL 以上のロールのみ（NG / TM は不可）。
- 参照・更新権限: ロール別可視範囲に準ずる。
- ステータス遷移: `PENDING（未対応）→ ONGOING（対応中）→ RESOLVED（解決済み）`（逆方向も可）。
- 重要度変更: `LOW（低）` / `MEDIUM（中）` / `HIGH（高）` 間の変更はいつでも可能。
- 対応担当者の変更: TL 以上のロールであればいつでも可能。ただし、担当者を未設定にすることはできない。
- 必ず対応期日を設定すること。
- ステータスを `RESOLVED（解決済み）` とする場合、完了期日を設定すること。
- 対応ログ（履歴）の追記は詳細画面から随時可能。削除は不可。

### 3.3 グループ・チーム管理

- グループ登録時: GL へ指定するユーザーを必須とする。
- チーム登録時: TL へ指定するユーザーを必須とする。
- 自分自身のアカウントは削除不可。

## 4. 提出期限

- 締切日は毎月 5 日（`DEADLINE_DAY = 5`）とする。
- 提出のリマインドは提出するまで、報告月の前月25日、当月は1日以降毎日行う。
- 締切の判定・通知・リマインドの仕様を変更する場合は、`API仕様書.md` と `UI設計書.md` の両方を更新する。
- 提出された月報へのTL以上のフィードバックは、報告月の翌月5日まで可能とする。

## 5. UI・データ仕様

### 5.1 ロール表示呼称

- NG: 新卒
- TM: メンバー
- TL: チームリーダー
- GL: グループリーダー
- OM: オフィスマネージャー
- SP: 営業担当者
- SM: 支店長
- SA: システム管理者

### 5.2 コンディション定義（4段階）

| UI表示 | API値 | 説明 |
|--------|-------|------|
| ◎ | BEST | 絶好調 |
| ○ | GOOD | まぁまぁ普通 |
| ▲ | WARN | ちょっと不調 |
| × | NG   | もうだめ最悪 |

- UI ↔ API 間は上記マッピングで相互変換する。
- コンディション自己診断の項目は 体調・ストレス・人間関係・悩み・疲れ・睡眠・やる気 の 7 項目固定。

### 5.3 月報ステータス（バッジ表示）

- `NotSubmitted`: 月報が未提出。
- `Checked`: `adminFeedback` が登録済み（回答あり）。
- `Reviewing`: `adminFeedback` が未登録（回答待ち）。

### 5.4 エスカレーション定義

- ステータス:
  - `PENDING（未対応）`
  - `ONGOING（対応中）`
  - `RESOLVED（解決済み）`
- 重要度:
  - `LOW（低）`
  - `MEDIUM（中）`
  - `HIGH（高）`

### 5.5 ダッシュボード仕様

- 提出期限バナーは全ロール共通でローダー直下（ヘッダー下）に固定表示する。
  - 今月（YYYY-MM）の残日数を表示。
  - 自分が今月分を提出済みか否かで表示を切り替える（未提出は警告、提出済みは完了表示）。
- TL 以上には以下を追加表示する。
  - 今月の提出完了率（%）と進捗バー。
  - 未提出メンバー一覧（チップ形式）。全員提出済みの場合は完了メッセージを表示。

### 5.6 月報詳細・フォームの表示順（維持すること）

1. 営業情報
2. 来月残業見込み（数値 + 理由）
3. 今月残業見込み（数値 + 理由）
4. コンディション自己診断（7項目）
5. コメント（問題点・意見など）
